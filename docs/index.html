El fallo que los paneles no enseñan

En estas aplicaciones el navegador habla directamente con la base de datos. Lo único que separa a un usuario de los datos de otro son las reglas de acceso de cada tabla (RLS). El problema habitual no es que falten:

-- "RLS activado": el panel muestra la tabla como protegida
alter table clients enable row level security;

-- …con una regla que deja pasar a cualquiera que haya iniciado sesión
create policy "clientes" on clients
  for all using (auth.uid() is not null);

Desde fuera, sin cuenta, no se ve nada. Pero cualquiera que se registre lee y modifica los clientes de todos los demás. Solo se descubre iniciando sesión con dos cuentas distintas y comparando.

Cómo es la revisión

  1. Desde fuera. Qué puede leer de tu app alguien sin cuenta: tablas, archivos y claves publicadas en el código.
  2. Entre usuarios. Dos cuentas de prueba, y la comprobación de si una recibe datos de la otra. Se hace en un entorno de pruebas o con datos ficticios.
  3. Reglas y código. Las reglas de acceso de cada tabla, las vistas, las funciones y las Edge Functions, leídas una a una.
  4. Informe. Cada problema con dónde está, qué se observó, por qué importa y el SQL exacto para arreglarlo. Y una llamada para repasarlo.

Lo que no es

  • No es una prueba de penetración completa ni una certificación.
  • No cubre la lógica de negocio ni los pagos.
  • No garantiza que la aplicación sea segura. Dice qué se comprobó, qué se encontró y qué quedó sin revisar.
  • Solo sirve para aplicaciones que usan Supabase desde el navegador.

Tus datos

Para saber si una tabla se filtra hay que pedirle filas: la comprobación entre usuarios descarga hasta 1.000 filas por cuenta y tabla y las compara en memoria. No se guardan y en el informe solo aparecen recuentos y nombres de columna, pero por eso mismo la prueba se hace en un entorno de pruebas o con datos ficticios, no con los datos de tus usuarios. No se escribe nada en tu base de datos.
