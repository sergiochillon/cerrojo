1. A user can modify other users’ rows

Where
public.clients
What was observed
Owner column: user_id. Result: account A updated 3 row(s) of the other; account B updated 2 row(s) of the other. The UPDATE set the column to its existing value, but it is a real write: it fires triggers and may have changed derived columns.
Why it matters
Verified on a disposable local database: one test account successfully ran an UPDATE on the other’s rows. A user can tamper with other people’s data.
How to fix it
Restrict update/delete to the owner:
create policy "modify own" on public.clients for update to authenticated using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id);

What was observed

drop policy if exists "<current policy>" on public.integration_tokens;

public.integration_tokens
What was observed

Why it matters
Anyone with the URL and the public key (both are in the site) can download these rows. Unless the table is public on purpose, this is a data leak.
How to fix it
Enable RLS and restrict reads to each row owner:
alter table public.integration_tokens enable row level security;
create policy "read own" on public.integration_tokens for select to authenticated using ((select auth.uid()) = user_id);

10. Edge Function uses the service key without checking the caller

Where

What was observed
supabase/functions/delete-account/index.ts: uses SERVICE_ROLE and no identity check was found (heuristic; review manually).
Why it matters

11. Users can edit their own row, which holds privilege columns

Where
public.profiles
What was observed
Columns: role, plan. Modifying policy: "Users can update own profile". The migrations do not revoke users’ UPDATE permission on these columns.
Why it matters
RLS filters rows, not columns. If the update policy lets users modify their row and that row stores role, plan or balance, they can change them from the browser console.
How to fix it
Move those columns to another table with no update policy, or revoke column update:
revoke update on public.profiles from authenticated;
grant update (<harmless columns>) on public.profiles to authenticated;

14. Policy only requires being signed in

Where
public.clients
What was observed
Policy "Authenticated users can manage clients" (all, roles: authenticated) with condition: using (auth.uid() is not null) · with check (auth.uid() is not null). supabase/migrations/20260901100000_esquema_inicial.sql
Why it matters
The most common flaw: RLS shows as "enabled" everywhere, but any registered user reaches everyone’s rows. Signing up is usually free.
How to fix it
drop policy "Authenticated users can manage clients" on public.clients;
create policy "read own" on public.clients for select to authenticated using ((select auth.uid()) = user_id);
create policy "insert own" on public.clients for insert to authenticated with check ((select auth.uid()) = user_id);
create policy "update own" on public.clients for update to authenticated using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id);
create policy "delete own" on public.clients for delete to authenticated using ((select auth.uid()) = user_id);
Create only the ones the app needs and verify with the isolation test (cerrojo aislamiento).

Limits of this report

  • This is a time-boxed review, not a security guarantee or certification.
  • Automated checks detect specific classes of flaws (RLS data exposure, published secrets, configuration). They do not cover business logic, payments, or attacks requiring interaction.
  • The isolation test is only conclusive for tables where the test accounts own data.
  • To check access, the tool downloads database rows (one per table without a session; up to 1,000 per account and table in the isolation test) and analyses them in memory. Their values are not stored in this report or on disk.
  • RPC and Edge Functions are not executed: they are reviewed manually.
  • Results reflect the state on the stated date. Any later change to tables or policies can introduce new flaws.
  • To check whether each table is readable without a session, one row per table was requested with the public key. Received values were discarded; the report only holds counts and column names.
  • Detected RPC and Edge Functions are not invoked automatically (they may have side effects). They need manual review.
  • The isolation test downloaded 41 full row(s) (cap: 1000 per account and table). They were processed in memory; this report only holds counts and column names.
  • The write test ran real UPDATE statements against a local database declared disposable. They set a column to its existing value, but fire triggers and may have modified derived columns (e.g. updated_at).
  • Migration analysis reflects what the repository says, not the live database state: changes made from the dashboard do not show up here.
  • Code review is pattern-based: it catches typical flaws and does not replace reading the Edge Functions and business logic.
